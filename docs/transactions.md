# Stage 8 transaction contract

**Decision checkpoint:** Task 8.2, 2026-09-21; implementation updated through Tasks 8.15–8.18 on 2026-09-23. This document records adopted implementation decisions for Tasks 8.3–8.30. Owner-backed SQL SELECT, INSERT, DELETE, explicit groups, implicit transactions, cursor lifetime, and managed programmatic insertion now use the shared lock/undo/completion path. The official requirements are `BEGIN TRANSACTION`, `END TRANSACTION`, safe concurrent access, and a threaded demonstration (`REQUIREMENTS.md` Section 7). The remaining details below are team design choices.

## Ownership and supported deployment

- One process owns each physical database directory through one canonical owner. Managed databases use `engine.database.Database`; the existing definition-driven mode temporarily uses `api.database.Database` until Stage 9 migrates it. Each owner shares one Catalog, runtime registry, transaction manager, lock manager, and availability state. Its session factory returns independent session facades; each session owns its current group, active result, and non-reentrant call guard. Transaction identity belongs to the session, not the worker thread. The existing `Database.engine` remains a default session for compatibility.
- Opening a second owner for the same resolved directory in the same process must fail while the first is live. Multiple processes sharing a directory, distributed transactions, and cross-process locks are unsupported; callers must not use them as a concurrent deployment. Closing one session never closes the owner's permanent handles. Owner close cancels/waits for sessions before closing them.
- The legacy owner constructs the same engine-level coordinator from its Catalog, `QueryEnvironment`, owned handles, stable database identity, and explicit table-to-file map; registered Sequential/clustered B+/Hash fixtures use that same adapter. One coordinator is attached to each owner and shared by all its sessions. Owner directory leases reject a second managed or legacy owner for the same resolved directory in one process. Directly constructed coordinators for test fixtures must likewise have one caller-managed owner; they do not claim a directory lease. The adapter never infers ownership from thread-local state or SQL names alone. Managed manifest v1 remains Heap plus supported B+ definitions; no manifest widening is implied. A naked `SqlEngine(QueryEnvironment(...))` or direct storage/index mutation is an exclusive/internal test or maintenance path, not a concurrent public session.
- The emergency HTTP admission guard stays in place until Stage 9 explicitly migrates request identity, every result variant, cancellation, and session lifetime. Core Stage 8 correctness is verified through engine sessions, not inferred from HTTP serialization.

## SQL and session lifecycle

- Exactly one statement is accepted per submission, with the Stage 7 comment, keyword, quoted-string, source-span, and optional final-semicolon behavior. `BEGIN TRANSACTION` starts an explicit group; `END TRANSACTION` commits it; `ROLLBACK` aborts it. `ROLLBACK` is a team addition. A `COMMIT` alias, nested groups, savepoints, scripts, and SQL `UPDATE` are unsupported. A complete parse precedes control effects, so `BEGIN TRANSACTION; INSERT ...` in one call neither begins nor writes.
- Standalone SELECT, INSERT, DELETE, and EXPLAIN ANALYZE use implicit transactions. A successful implicit mutation commits before returning. A successful statement inside an explicit group reports a **provisional** affected-row count; the group becomes committed only after successful END. A session reads its own uncommitted changes.
- The transaction state sequence is `ACTIVE -> COMMITTING -> COMMITTED` or `ACTIVE/COMMITTING -> ABORTING -> ABORTED`; restoration failure yields `ABORT_FAILED` and owner quarantine. A session with no active group is `IDLE`. Terminal reports remain distinguishable from the reusable session. No terminal state is claimed until synchronization or restoration has completed.
- Nested BEGIN, END/ROLLBACK without an active group, a simultaneous call on the same session, a second statement with an open SELECT result, and END with an open result are protocol errors. They do not silently commit or abort the current group. The caller may close/drain the result or request ROLLBACK. ROLLBACK and session close close owned results before undo. A later END after automatic abort is a protocol error; a fresh BEGIN is required for a new explicit group.
- An ordinary **execute** error in an explicit group aborts the whole group, including prior successful statements. This covers malformed or unsupported SQL submitted to execute, binding/validation failures, constraints, lock timeout/deadlock, operator errors, mutation failures, and CREATE inside the group. A pure `prepare`/`describe` error has no transaction side effect. A failed implicit statement aborts its one-statement transaction. The original error and final abort outcome are both reported.
- An implicit SELECT holds protection until EOF or explicit early close; then its read-only group ends. An explicit SELECT closes its cursor at EOF/early close but retains transaction locks through END/ROLLBACK. Cursor iteration and session execution are serialized per session; independent sessions may run on distinct threads. Plain EXPLAIN is metadata-only and opens no row cursor. ANALYZE performs exactly one protected SELECT execution.

## Isolation, resource order, and physical safety

- Use table-level shared (`S`) locks for SELECT sources and exclusive (`X`) locks for INSERT/DELETE targets. Hold **both S and X until terminal commit or completed abort**: rigorous two-phase locking. Missing-key and range reads receive the same table S protection, preventing covered phantoms. Joins acquire all distinct base tables in stable identity order. Aliases and access paths share one table resource identified by database identity and stable table identity; each index belongs to its base table's resource.
- A database schema gate is acquired before table resources. Ordinary transaction execution holds schema S until the group ends; standalone CREATE obtains schema X through validation, file initialization, Catalog/runtime publication, manifest replacement, and cleanup. CREATE inside an explicit group is rejected and aborts that group, with no hidden commit. Pure prepare/describe and metadata lists hold a short schema gate and no data lock if truly metadata-only. Planning helpers that touch index data must instead run under data S.
- Different owners' S/S grants are compatible; S/X and X/X are incompatible. Reacquiring one's own sufficient lock is idempotent. An S-to-X upgrade keeps S while waiting. FIFO request order admits a compatible leading reader batch, prevents later readers from overtaking a queued writer, and includes upgrades. Waits use conditions and predicate rechecks; no busy loop holds a manager or physical latch.
- A wait-for graph includes incompatible holders and queue-order blockers. When a new wait closes a cycle, the requesting transaction is the victim; its **whole group** is aborted before a conflicting request gains access. An acyclic wait has a configurable finite default deadline of 30 seconds and ends in a separately reported timeout. Cancellation is another distinct abort cause. The engine never silently retries SQL or a business operation; the application may retry the entire operation using fresh reads.
- Logical locks do not make the shared `PageManager` file offset, headers, caches, and counters thread-safe. Short latches or safe positional I/O protect complete seek/read/write operations, mutable index state, registry publication, replacement, and close. No thread waits for a transaction lock while holding a physical, registry, session-manager, or lock-manager latch; no physical latch spans a yielded row or user think time. Independent tables and compatible readers must demonstrably overlap, so a whole-database execution mutex is not the final implementation.
- Prepared plans currently retain borrowed object identities. After acquiring execution locks, validate Catalog and runtime generations and rebind or reject a stale plan before data access. Restoration or replacement increments per-table generation and refreshes canonical runtime objects, including adapters that borrow storage. A waiter never resumes on a stale pointer.

## Before-image undo, commit, and failure

- After target X and before the first permanent mutation of a table, including validity-marker writes, capture one consistent image of its **complete physical file set**: base file, every associated index, headers/free lists, and permanent validity state. Record original lengths and paths. Reuse the original snapshot for later writes to that table in the same group. No read-only snapshot and no whole-database or global manifest snapshot. Separate table snapshots preserve another transaction's commit to an independent table.
- Flush the pre-write set, copy files in bounded chunks to a transaction-owned undo directory, and publish a complete descriptor before any mutation. A failed or over-budget capture cleans partial copies and aborts without writing base/index state. Adopt initial configurable owner limits of **64 live sessions, 32 active transactions, 1 GiB undo per transaction, and 2 GiB total undo**, with **1 MiB copy chunks**, at most **two concurrent captures** and two extra copy handles per capture. Reserve owner quota atomically across concurrent captures and require at least the exact remaining capture bytes plus a **64 MiB free-space reserve** before copying. These are policy defaults to implement and test in 8.3/8.11; changing them requires documented evidence, not an implicit unbounded path. Existing operator memory/handle budgets remain separate.
- Abort retains X and schema protection while it closes cursors/spools, restores exact bytes and lengths of every changed table/index, removes only transaction-owned replacement artifacts, reopens canonical handles, refreshes caches/headers/free-space and borrowed adapters, bumps generations, and validates base/index agreement. Ordinary Stage 7 maintenance repair may run during an operation, but transaction abort must restore the group's original state, including earlier successful statements. A failed restore or validation makes the owner unavailable **before** waiters can access it. Cancel waits, keep diagnostics and undo artifacts, and report `ABORT_FAILED`; closing a bad handle is not repair.
- END first rejects an open result, then validates and synchronizes the whole modified set using flush/fsync. The success point is after all required validation/synchronization succeeds and the transaction becomes `COMMITTED`, while locks are still held. Only then release locks and discard undo. A pre-success failure attempts full abort. A post-success snapshot-cleanup failure is a warning/artifact debt, never a fictitious rollback; a later clean reopen must reject unresolved artifacts until they are explicitly inspected/removed.
- Maintain an owner unclean-close marker while undo-bearing transactions or unresolved artifacts exist. Successful orderly completion removes the marker only after all owned artifacts are accounted for. A fresh open that finds a marker or orphan undo data **refuses normal access** and requires explicit external inspection/repair; Stage 8 does not replay recovery automatically. A failed restore requires this repair policy even after process restart. Clean close/reopen must retain committed rows and exclude successfully aborted writes.
- These are **ordinary in-process atomicity and clean-reopen guarantees**, not crash-atomic multi-file commit, WAL, redo, or power-loss recovery. Writes may reach disk before END; undo is therefore required. Snapshot cost is proportional to the first-written table and all its indexes, and its time/I/O are reported separately from query execution.

## Implementation and acceptance boundary

Tasks 8.3–8.6 provide immutable state snapshots, owner-scoped IDs/errors, independent control sessions, handwritten control AST/parser rules, and metadata-only table/file access plans. Tasks 8.7–8.10 add a shared S/X lock manager with FIFO queues, S-to-X upgrades, condition waits, finite timeout, cooperative cancellation, wait-for cycle detection and requesting-participant victim policy. Schema S/X grants precede table grants. A failed waiter retains earlier locks until its transaction finishes abort cleanup; `release_all` accepts only completed COMMITTED or ABORTED reports and is idempotent. Quarantine refuses grants and wakes waiters. Immutable snapshots expose holders, waiters and graph blockers. The manager condition never encloses disk I/O or a blocking physical latch.

`PageManager` uses one short reentrant latch per owned handle for complete seek/read/write, allocation, header/counter updates, replacement, flush and close. Hash typed counters take a transfer delta under that same latch; mutable hash structural counters, Catalog and runtime registration have separate short latches. The latch order is typed hash I/O → page handle; QueryEnvironment → Catalog during validation. Logical lock waits happen outside all of these latches. Runtime registry changes increment a per-table generation; access plans recheck it before reuse. A page or registry latch does not span an iterator yield. Concurrent raw writers remain outside the supported public session contract.

`Database.open_session().execute(...)` and the compatibility `Database.engine.execute(...)` now use the same session coordinator. SQL is fully parsed before transaction effects, resource intents are acquired before binding/runtime validation, and access generations are checked after waits. A waiter that observes rollback-driven handle replacement refreshes its access plan and rebinds a prepared query while holding the granted resources. Standalone SELECT holds its implicit transaction through EOF or close; an explicit SELECT releases operator resources at EOF/close but retains logical locks until END/ROLLBACK. INSERT and DELETE acquire table X and publish the first-write image before calling the existing maintenance service. Their explicit-group `CommandResult` is provisional until END; an implicit command commits before return. `Database.insert(...)` joins the default explicit group or creates an implicit write. The old `session.run_write(table_name, action)` remains only as a dynamically scoped fault-injection hook for foundation tests.

Tasks 8.11–8.14 add `UndoStore`, `TableRuntime`, and `CompletionService`. The store reserves exact image bytes under an owner mutex, checks disk reserve, limits two concurrent bounded copies, hashes each file, and publishes one fsynced descriptor per first-written table. The marker `.minidb_unclean` and nonempty `.minidb_undo` refuse fresh opens; Stage 8 does not replay either. Abort retains logical protection while closing affected canonical handles, replacing bytes, reopening storage/index adapters, validating scans and index coverage, and bumping resource generations. END validates and flushes all modified tables before entering COMMITTED with locks held; image cleanup follows lock release, and cleanup failure is a warning with retained artifacts. Restore failure produces ABORT_FAILED, quarantines the owner before waiters can run, and retains images for inspection. Managed and legacy owners expose configurable `UndoLimits` when created/opened. Evidence is in `docs/ETAPA_08_TASK_8_11_8_14.md`.

Tasks 8.15–8.18 integrate SELECT/INSERT/DELETE and their existing storage/index adapters. Tasks 8.19–8.22 complete the dedicated CREATE, EXPLAIN/ANALYZE, observability, cancellation, and shutdown work. Tasks 8.23–8.27 prove controlled schedules, failure restoration, a real unsafe/protected threaded comparison, and regression compatibility. Task 8.28 hands the session contract to Stage 9. The Stage 7 audits remain historical; their partial-failure descriptions remain accurate for deliberately standalone lower-level engines, while an owner-coordinated session has the stronger group-level contract.
